# 工作模式

刚上手 CC 的时候，你最先需要搞懂的就是它的工作模式。CC 不是那种一股脑执行命令的工具，它有自己的一套工作逻辑，搞懂了能让你事半功倍。

CC 提供了三种模式，各有分工：

| 模式 | 干什么用的 |
| --- | --- |
| **默认模式** | 刚启动时的状态，你可以跟 CC 聊天、问问题、做简单任务，就是一个增强版的对话框。 |
| **计划模式** | 当任务比较复杂时，CC 会进入这个模式。它会先分析需求、拆解步骤，但不动你的代码，纯做规划。 |
| **Accept Edits 模式** | 规划完了，该动手了。这个模式下 CC 会真正开始改代码、写文件。 |

默认情况下，CC 接到任务后会自动进入**计划模式**。你可以用 `Shift + Tab` 在这三种模式之间自由切换。

[图片]

### 三种模式怎么选

- **问问题、查资料**：用默认模式就够了
- **改代码、写功能**：先让它进计划模式规划，确认方案后再切到 Accept Edits 让它动手
- **小修改、快速修复**：直接切到 Accept Edits 模式，省去规划环节

### 免确认模式（危险模式）

如果你想让 CC 一路畅通不用每次确认，可以退出后用这个命令重启：

```bash
claude --dangerously-skip-permissions
```

这个模式下 CC 会跳过所有权限确认，直接执行操作。适合你自己一个人开发、对代码有完全控制权的时候用。**注意：在生产环境或者不确定的操作上千万别开这个模式。**

### 终端命令确认

在 Accept Edits 模式下执行终端命令时，会弹出三个选项：

[图片]

- **仅同意这一次** — 放行当前这一条命令，下次还得确认
- **同意并记住** — 不仅这次放行，以后该项目的依赖安装类命令也不再询问，省心
- **不同意** — 拒绝执行，继续商量，CC 会换个方案

# 指令大全

CC 的指令系统是它的核心操作入口，熟练用好这些指令能让你的效率翻倍。

| 指令 | 用途 |
| --- | --- |
| `/compact` | 手动压缩上下文 |
| `/plugin` | 安装和管理插件 |
| `/btw + 任务` | 临时切出当前项目，隔离上下文干点别的，完事按 `Esc` 回来 |
| `/init` | 生成项目级 `Claude.md` 配置文件 |
| `/mcp` | 管理 MCP 服务器连接和 OAuth 认证 |
| `/simplify` | 一键代码审查，会从质量、性能、复用性三个角度审一遍，然后自动改 |
| `/skills` | 管理已下载的技能 |
| `/context` | 查看当前上下文占用情况 |
| `/memory` | 管理全局/项目记忆和 Auto Memory |
| `/review` | 本地代码审查 |
| `/model` | 切换模型档位（用了 CC Switch 接第三方模型的话，这条没啥用） |
| `/clear` | 清空上下文，等于开新会话 |
| `/hooks` | 查看和配置事件钩子 |
| `/resume` | 在新窗口里恢复之前的对话 |
| `/help` | 查看所有指令的完整说明 |
| `/agents` | 创建和管理子 Agent |
| `/rewind` | 回滚操作（连按两下 `Esc` 也能达到同样效果） |

### 高频指令详解

**`/compact` — 上下文压缩**

上下文快满的时候用，会把之前的对话精简成摘要释放空间。可以带上提示词告诉 CC 哪些内容要保留。

**`/btw` — 临时对话**

这个超好用。比如你正在改项目 A 的代码，突然想问个跟项目无关的问题，用 `/btw` 隔离上下文，完事按 `Esc` 回来继续改代码，不会污染主会话。

**`/simplify` — 代码审查**

让 CC 从三个维度审查你的代码：质量、性能、复用性。审查完自动优化修改，适合写完一段代码后让 CC 帮你"体检"一下。

**`/rewind` — 回滚**

改错代码了？连按两下 `Esc` 或者输入 `/rewind` 就能回滚到之前的状态，比自己手动 git 恢复方便多了。

# 上下文管理

上下文就像 CC 的"短期记忆"，容量有限，需要你主动管理。

为什么这很重要？因为 CC 每次跟你对话，都会把之前的聊天记录塞进上下文窗口里。用着用着，上下文就会越来越满，CC 的反应会变慢，甚至可能丢失前面聊过的关键信息。所以学会管理上下文，是用好 CC 的基本功。

## 查看上下文进度

随时输入 `/context` 看看当前还剩多少空间：

```bash
/context
```

[图片]

它会告诉你这些信息：

| 信息项 | 含义 |
| --- | --- |
| **总 token 数** | 当前使用量 / 上限（比如 77.8k / 200k） |
| **占用百分比** | 一眼看出还能聊多久 |
| **各项占用明细** | 系统提示词、工具定义、记忆文件、历史消息各占多少 |
| **Autocompact buffer** | 系统预留的自动压缩缓冲区，这部分不用担心 |

重点关注两个数字：**占用百分比**和**消息占比**。消息占比越大，说明你的聊天记录越长，离压缩越近。

## 什么时候该压缩

别等到 CC 提醒你，这几个信号出现就该动手了：

- **占用超过 60% - 70%**：这是最直观的指标，看到黄色区域扩大就准备压缩
- **CC 响应变慢**：上下文越长，CC 处理越慢，以前秒回现在等半天
- **CC 开始"断片"**：你明明说过某个需求，CC 却不记得了，说明信息被挤掉了
- **完成阶段性任务**：比如刚做完登录模块，准备开始做支付模块，趁这个节点压缩一下
- **切换工作方向**：从修 bug 改成写新功能，压缩一下让 CC 重新聚焦

## 压缩上下文

用 `/compact` 可以手动压缩，把之前的对话精简成摘要，释放空间：

```bash
/compact
```

### 进阶用法

压缩的时候可以带上提示词，告诉 CC 哪些信息需要保留：

```bash
/compact 保留关于登录模块的所有设计决策和代码修改
```

```bash
/compact 重点保留数据库表结构相关的讨论，其他可以精简
```

这样 CC 压缩时会优先保留你指定的内容，避免重要信息被丢掉。

### 压缩时机建议

- **60% 左右**：轻度压缩，影响最小
- **75% 左右**：必须压缩，否则可能丢失信息
- **90% 以上**：赶紧压缩，否则 CC 可能无法正常工作

## 清空上下文

如果当前会话实在太乱，不如推倒重来。`/clear` 会彻底清空上下文，相当于开一个全新的会话：

```bash
/clear
```

### 什么时候用 `/clear`

- 会话太长，压缩也救不回来了
- 之前的上下文跟当前任务完全无关
- CC 的行为变得很奇怪，需要重置状态
- 换了一个完全不同的开发任务

### 注意事项

- 清空后之前的对话记录就没了
- 如果之前有重要的设计决策，确保已经写进 `Claude.md` 或记忆
- 可以先用 `/resume` 保存当前会话，再清空开新的

## 状态栏常驻显示

每次手动输入 `/context` 太麻烦？可以让上下文占用情况常驻在状态栏，一眼就能看到。

输入以下提示词，按 CC 引导完成后重启终端：

```bash
帮我配一个 statusLine,显示当前目录+模型+上下文剩余百分比（进度条显示）
```

[图片]

配置好之后，终端底部会一直显示：

- **当前目录**：知道你在哪个项目里
- **模型名称**：知道当前用的是哪个模型
- **上下文进度条**：直观看到还剩多少空间

这样就不用每次都手动查了。

## 对话恢复

不小心关了窗口或者切换了项目，想找回之前的对话？用 `/resume` 挑一个恢复就行：

```bash
/resume
```

[图片]

它会列出你之前的会话记录，每个会话会显示时间戳和简短预览。选择一个就能接着聊，上下文完整保留。

### 恢复场景

- **误关窗口**：手滑关了终端，对话还在
- **切换项目**：从项目 A 切到项目 B，完事了想回来继续
- **中断续写**：昨天聊到一半，今天想接着聊

## 多会话管理小技巧

- **按任务拆分会话**：一个会话专注做一件事，做完就开新的，别把所有事塞进一个会话。上下文干净，CC 执行效率更高
- **善用 `/btw`**：临时有别的事要问，用 `/btw` 隔离上下文，完事按 `Esc` 回来继续。不会污染主会话
- **重要决策及时记录**：把关键的设计决策写进 `Claude.md` 或让 CC 写进记忆，这样即使清空上下文也不会丢失
- **阶段性压缩**：完成一个功能模块就压缩一次，保持上下文"年轻"
- **会话命名习惯**：给每个会话一个明确的目标，比如"重构登录模块"而不是"改代码"，方便后续恢复时快速找到

# Claude.md 配置

`Claude.md` 是 CC 的"项目说明书"和"个人偏好设置"，相当于告诉 CC "你是谁、怎么干活"。

CC 启动时会自动读取这个文件，里面写的内容会直接影响它的行为。比如你写"永远用中文回复"，那 CC 就会一直说中文；你写"写代码时加注释"，它就会乖乖加注释。

## 项目级 Claude.md

在项目根目录下生成一份，CC 会自动读取：

```bash
/init
```

项目级配置只对当前项目生效，适合放跟项目相关的内容。

## 全局级 Claude.md

全局配置影响所有项目，适合放一些通用偏好。

**方式一：直接对话**

跟 CC 说一句话，它会帮你写进去：

```bash
回答时永远说中文，写进全局claude.md
```

**方式二：指令编辑**

输入 `/memory`，选择「User Memory」进入编辑界面：

[图片]

### 通用偏好示例

不知道该写什么？这几个常用偏好可以直接抄：

**语言偏好**

```bash
回答时永远说中文，写进全局claude.md
```

**代码风格**

```bash
写代码时默认用 TypeScript，变量命名用 camelCase，写进全局claude.md
```

**回复风格**

```bash
回复要简洁，不要废话，直接给结论和代码，写进全局claude.md
```

**Git 提交**

```bash
提交代码时使用中文 commit message，格式为"类型: 简短描述"，写进全局claude.md
```

**代码规范**

```bash
写代码时不要加注释，除非逻辑特别复杂，写进全局claude.md
```

**安全习惯**

```bash
永远不要在代码里硬编码密钥、密码或 API Key，写进全局claude.md
```

**错误处理**

```bash
代码出错时先分析原因，给出修复方案而不是直接重写，写进全局claude.md
```

**项目级 Claude.md 也可以写这些**

项目级配置适合放跟当前项目相关的内容，比如：

- 项目的技术栈和架构说明
- 代码规范和命名约定
- 常用的 API 端点
- 数据库表结构
- 部署流程

### Claude.md 的作用机制

CC 启动时会按顺序加载多个配置：

1. **全局级** — 所有项目通用的偏好
2. **项目级** — 当前项目的特定配置
3. **目录级** — 当前目录下的配置（如果有的话）

后面的配置会覆盖前面的，所以你可以在全局层设"用中文"，但在某个英文项目里设"用英文"。

# Auto Memory

Auto Memory 是 CC 的自动记忆功能。开启后，它会在你工作过程中自动记下你的习惯、踩过的坑和积累的经验。

### Auto Memory 记什么

- 你纠正过 CC 的错误做法
- 你喜欢的代码风格和回复方式
- 项目中的特殊约定和坑
- 你反复强调的需求

### 什么时候生效

- 你告诉 CC "不要这样做"，它会记住下次不犯
- 你确认了某个方案可行，它会记住这个偏好
- 你踩过一个坑，它会记录下来避免重复

### 注意事项

- 记忆只对当前项目生效，不会跨项目串台
- 可以通过 `/memory` 查看和管理已有记忆
- 如果记忆过时了，可以手动删除或更新

开启方式：输入 `/memory`，选择「Auto-memory」然后回车：

# 能力扩展（进阶内容）

CC 本体功能已经很强了，但它的扩展生态才是真正的杀手锏。

## Skill 技能扩展

Skill 是 CC 的技能包，装上之后能解锁新能力。比如原本 CC 不会设计前端界面，装上 Frontend-Design 技能后，它就能做出有设计感的 UI 了。

### 推荐 Skill

直接把 GitHub 链接发给 CC，它会帮你装好：

| 技能名称 | 作用 | 来源 |
| --- | --- | --- |
| Find-Skill | 帮你搜索和安装社区技能，相当于技能商店 | [GitHub](https://github.com/vercel-labs/skills/tree/main/skills/find-skills) |
| Frontend-Design | 前端界面设计专家，能做出有设计感的 UI | [GitHub](https://github.com/anthropics/skills/tree/main/skills/frontend-design) |
| Skill-Creator | 自己动手造技能，支持创建、修改和评估 | [GitHub](https://github.com/anthropics/skills/tree/main/skills/skill-creator) |

### 手动安装 Skill

除了让 CC 自动安装，你也可以去这些网站自己找技能手动装：

- [skills.sh](https://www.skills.sh/) — Skill 搜索和分享平台
- [LobeHub Skills](https://lobehub.com/zh/skills) — 按分类浏览，有精选合集

### 安装 Skill

下载后，把文件放到对应目录就行，或者可以用 cc-switch 进行统一管理：

[图片]

### Skill 的存放位置

- **全局级**：放在 `~/.claude/skills/` 目录下，所有项目都能用
- **项目级**：放在项目根目录的 `.claude/skills/` 目录下，只对当前项目生效

## MCP 扩展

MCP（Model Context Protocol）是 CC 与外部工具和服务对话的桥梁。简单来说，装上 MCP 服务器后 CC 就能直接操作数据库、调用 API、操作文件系统等等。

### MCP 能干什么

- 连接数据库，直接执行 SQL 查询
- 调用第三方 API（比如天气、翻译、新闻）
- 操作文件系统（批量重命名、格式转换）
- 连接 Slack、飞书等通讯工具

想深入了解 MCP 的具体玩法，可以去哔哩哔哩看秋芝2046大佬的相关视频

## CLI 命令行工具

CLI 工具可以跟 CC 配合使用，让 CC 帮你操作各种命令行工具。

把下载链接丢给 CC，让它全自动帮你装好：

| 工具名称 | 功能简介 | 来源 |
| --- | --- | --- |
| OpenCLI | 万能命令行工具箱，把各种网站和应用统一成命令行操作 | [GitHub](https://github.com/jackwener/opencli) |
| GitHub CLI | GitHub 官方出品，PR、Issue 直接在终端操作 | [GitHub](https://github.com/cli/cli) |

### 安装 CLI 的正确姿势

把 GitHub 链接发给 CC，跟它说"帮我装一下这个"就行：

```bash
帮我装一下这个CLI工具：https://github.com/cli/cli
```

CC 会自动判断你的系统，选择合适的安装方式，省去你自己查文档的麻烦。

## 子 Agent（SubAgent）

子 Agent 就是 CC 的"分身术"，可以让多个 Agent 并行干活，效率拉满。

### 为什么要用子 Agent

- **并行处理**：一个 Agent 改前端，另一个改后端，同时进行
- **专注分工**：每个 Agent 专注一件事，减少上下文污染
- **隔离上下文**：子 Agent 有自己的独立上下文，不会互相干扰

### 怎么触发

- **自动触发**：任务复杂、有并行可能时，CC 会自己派生子 Agent
- **手动创建**：用 `/agents` 指令，进入 Library 界面自己搭

### 创建流程

1. 选择创建范围 — 项目级还是全局级
2. 选择「AI 辅助创建」，让 AI 帮你搭
3. 描述这个子 Agent 要干啥（越具体越好）
4. 给它分配工具权限（打勾的就是启用的）
5. 选模型，Sonnet 就够用（用了 CC Switch 的话选哪个都一样）
6. 选个颜色，跟主 Agent 区分一下

### 子 Agent 使用技巧

- **给它明确的角色**：比如"你是前端专家，负责所有 React 组件的开发"
- **限定工具权限**：只给它需要的工具，避免它乱动
- **用不同颜色区分**：主 Agent 用蓝色，子 Agent 用绿色，一目了然

## Hook 钩子

Hook 是"触发器"，能在特定事件发生时自动跑脚本。比如你让 CC 改完代码后自动格式化，或者提交前自动检查有没有安全问题。

### 实用 Hook 示例

**任务完成提醒**

```bash
设置一个hook，每次完成任务之后，都自动执行一个声音脚本，发出一个提示音"叮"进行提醒
```

**自动格式化代码**

```bash
设置一个hook，每次修改文件之后，都自动运行 prettier 格式化代码
```

**提交前安全检查**

```bash
设置一个hook，每次提交代码之前，都会自动触发代码格式和安全问题的检查
```

**自动运行测试**

```bash
设置一个hook，每次修改文件之后，都自动运行相关的单元测试
```

**防止提交敏感信息**

```bash
设置一个hook，每次提交之前检查有没有包含密码、密钥、API Key等敏感信息
```

**自动同步文档**

```bash
设置一个hook，每次修改 README 文件之后，自动生成目录结构文档
```

**清理临时文件**

```bash
设置一个hook，每次完成任务之后，自动清理 dist、node_modules 等临时目录
```

**代码规范检查**

```bash
设置一个hook，每次修改文件之后，自动运行 eslint 检查代码规范
```

### Hook 的触发时机

- **PreToolUse**：工具执行前触发（比如文件修改前）
- **PostToolUse**：工具执行后触发（比如文件修改后）
- **Notification**：通知时触发（比如任务完成时）

## 插件（Plugin）

插件是个"全家桶"概念，一个插件可能打包了 Skill + SubAgent + Hook + MCP，装一个顶好几个。

### 插件 vs 单独组件

- **Skill**：只是一个技能，轻量级
- **Plugin**：包含多个组件，功能更完整

### 安装和管理

1. 输入 `/plugin` 进入插件商店
2. 选中喜欢的插件安装，或者管理已装的插件

### 推荐插件

| 插件名称 | 干什么的 | 来源 |
| --- | --- | --- |
| commit-commands | Git 操作一键搞定，提交、推送、创建 PR 全包 | [GitHub](https://github.com/anthropics/claude-code/tree/main/plugins/commit-commands) |

### 找更多插件

- [Claude Code 官方插件](https://claude.com/plugins#plugins) — 官方精选
- [Claude Code Plugins](https://claudecodeplugins.dev/zh) — 社区贡献的插件合集
