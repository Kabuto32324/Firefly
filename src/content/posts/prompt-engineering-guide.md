## 一个真实的翻车现场

上周有个朋友问我："我让 Claude 帮我写个登录功能，它给我生成的代码跑都跑不通，是不是这工具不行？"

我看了他的 Prompt：

> "帮我写一个用户登录功能"

五个字，言简意赅。

然后 Claude 给了他一堆代码，有前端表单、有后端验证、有数据库查询。问题是他只是个前端，没有后端环境，代码自然跑不通。

AI 理解了你要什么，但它不知道你的情况、不知道你要什么格式、不知道你的技术水平。这篇文章就来解决这个问题。

---

## 先聊点原理：AI 是怎么读你的 Prompt 的

在讲技巧之前，先花两分钟搞清楚一个事：你写的 Prompt，AI 到底是怎么"看"的？

### Token 化

你写的"帮我写一个登录功能"，AI 看到的不是这 8 个字，而是被拆成了若干个 token。中文大概一个字一个 token，英文可能是单词或者词根。

这意味着什么？你的用词越精准，token 越少，AI 理解起来越轻松。

### 上下文窗口

AI 有"短期记忆上限"，就是上下文窗口。你之前说的所有话都会塞在这个窗口里，塞满了就会开始"遗忘"早期内容。

所以如果你的 Prompt 太长，或者对话太多轮，AI 可能会忘掉你最开始说的需求。

### 注意力机制

AI 会特别关注你 Prompt 里的"信号词"。比如你说了"用 TypeScript"，它就会更倾向于生成 TS 代码；你说了"简洁一点"，输出就会更精简。

后面讲的技巧，其实就是利用这个机制——通过特定的表达方式，引导 AI 把注意力放在正确的地方。

### 温度和采样

同一个 Prompt 问两遍，结果可能不一样。这是"温度"在起作用——温度越高，输出越随机发散；温度越低，越稳定保守。

理解这点后你就知道：Prompt 写得好，能降低随机性，让输出更稳定。

## 8 个实战技巧

每个技巧都配一个"反面 vs 正面"的对比，直观展示差距。

### 技巧 1：角色设定

给 AI 一个身份，回答质量会明显提升。

**反面教材：**
```
帮我写一个登录功能
```

**正面教材：**
```
你是一个有 5 年经验的前端开发工程师，熟悉 React 和 TypeScript。
请帮我写一个用户登录功能，包含表单组件和提交逻辑。
```

AI 会根据角色调整输出的风格和深度。你给了它"前端工程师"的身份，它就不会给你生成后端代码。

### 技巧 2：明确任务边界

一次只做一件事。你想写登录功能，就别让 AI 同时设计数据库。

**反面教材：**
```
帮我做一个完整的登录注册系统，包括前端、后端、数据库设计
```

**正面教材：**
```
我需要一个前端登录表单组件，用 React + TypeScript。
功能：邮箱密码输入、表单验证、提交到 /api/login。
不需要后端，我自己处理。
```

拆得越细，AI 给的东西越精准。分几个 Prompt 来完成，每次专注一个模块。

### 技巧 3：Few-shot 示例

给 AI 看几个例子，比你描述半天管用。

**反面教材：**
```
帮我写一个用户信息的 TypeScript 类型定义
```

**正面教材：**
```
帮我定义一个用户信息的 TypeScript 类型。
参考这个格式：

interface Product {
  id: string;
  name: string;
  price: number;
  tags: string[];
  createdAt: Date;
}

请按同样的风格定义一个 User 类型，包含 id、name、email、avatar、role 这些字段。
```

AI 看到例子就能准确模仿格式和风格，不需要你解释"我想要 camelCase 命名、用 interface 不用 type"这些细节。

### 技巧 4：输出格式约束

明确告诉 AI 你要什么格式。

**反面教材：**
```
帮我分析一下这个项目的代码质量
```

**正面教材：**
```
请用以下格式分析这个项目的代码质量：

## 整体评分（1-10）

## 优点
- 

## 问题
- 

## 改进建议
- 
```

有格式约束，AI 的输出就是结构化的，直接能用，不用你再手动整理。

### 技巧 5：分步拆解

复杂任务别指望一句 Prompt 搞定，拆成小步骤。

**反面教材：**
```
帮我重构这个函数，让它更优雅、性能更好、还要加错误处理
```

**正面教材：**
```
这个函数有几个问题，我们一步步来。

第一步：先帮我分析一下这个函数有哪些问题（可读性、性能、错误处理）。
等你分析完，我们再进行下一步。
```

分步的好处：每一步 AI 的注意力更集中，输出质量更高。而且你能及时纠正方向，避免 AI 一上来就跑偏。

### 技巧 6：上下文管理

给 AI 足够的背景信息，但别给太多。

**反面教材：**
```
这个组件渲染不出来，帮我看看
```

**正面教材：**
```
这是一个 React 组件，用于显示用户列表。
问题：页面加载后组件显示空白，控制台没有报错。
技术栈：React 18 + TypeScript + Tailwind CSS。
我怀疑是数据没有正确传入，但不确定。

请帮我排查可能的原因。
```

背景信息给到位，AI 能更快定位问题。但注意别把项目的全部代码都塞进去，挑和问题相关的关键信息就够了。

### 技巧 7：负向指令

告诉 AI **不要做什么**，有时候比告诉它做什么更有用。

**反面教材：**
```
帮我写一个 API 接口文档
```

**正面教材：**
```
帮我写一个 REST API 接口文档。

要求：
- 用中文
- 包含请求方法、路径、参数说明、响应示例
- 不要用 Markdown 表格（我要嵌入到文档系统里）
- 不要加"简介"、"概述"这些废话，直接上干货
```

负向指令适合控制输出的"废话量"。你越明确说不要什么，AI 就越克制。

### 技巧 8：迭代优化

第一次不满意很正常，关键是知道怎么调。

**第一轮：**
```
帮我写一个 React 登录表单
```
（结果太简单，没有样式）

**第二轮：**
```
基于上一轮的代码，加一下这些改进：
1. 用 Tailwind CSS 做样式
2. 加上表单验证（邮箱格式、密码最少 6 位）
3. 提交按钮加 loading 状态
```
（结果好多了，但验证逻辑不对）

**第三轮：**
```
验证逻辑有点问题：
- 邮箱应该用正则校验，不能只检查有没有 @
- 密码强度不够，要求至少包含字母和数字
- 错误提示要显示在输入框下方
```

三轮下来，一个"能用"的表单就变成了"好用"的表单。别指望一步到位，迭代是常态。

## 实战：登录功能的进化

把这 8 个技巧串起来，看一个 Prompt 从"能用"到"好用"的完整过程。

### 第一轮：能用

```
帮我写一个用户登录功能
```

结果：一堆代码，前后端都有，完全不符合你的需求。

### 第二轮：角色 + 边界 + 格式

```
你是一个前端开发工程师，熟悉 React + TypeScript + Tailwind CSS。

帮我写一个用户登录表单组件。

要求：
- 邮箱 + 密码两个输入框
- 表单验证（邮箱格式、密码最少 6 位）
- 提交按钮
- 用组件化的写法

只写前端组件，后端我自己处理。
```

结果：干净多了，代码风格统一，功能也对。

### 第三轮：加上示例 + 负向指令

```
你是一个前端开发工程师，熟悉 React + TypeScript + Tailwind CSS。

帮我写一个用户登录表单组件。

参考这个组件的风格：

interface ButtonProps {
  variant: 'primary' | 'secondary';
  size: 'sm' | 'md' | 'lg';
  loading?: boolean;
  onClick: () => void;
  children: React.ReactNode;
}

要求：
- 邮箱 + 密码两个输入框
- 表单验证（邮箱格式、密码最少 6 位）
- 提交按钮带 loading 状态
- 用组件化的写法
- 不要用 class 组件
- 不要加任何样式库，用原生 CSS 或 Tailwind

只写前端组件，后端我自己处理。
```

代码风格和你项目一致，功能完整，没有多余的东西。

## 总结速查表

| 技巧 | 核心要点 | 一句话说明 |
|------|---------|-----------|
| 角色设定 | 给 AI 一个身份 | "你是一个前端工程师" |
| 任务边界 | 一次只做一件事 | 别让 AI 同时干三件事 |
| Few-shot | 给例子比描述管用 | 贴个参考格式 |
| 输出格式 | 明确要什么格式 | JSON、表格还是列表 |
| 分步拆解 | 复杂任务拆成小步 | 先分析，再动手 |
| 上下文管理 | 给足背景信息 | 说清楚技术栈和问题 |
| 负向指令 | 说清楚不要什么 | "不要废话" |
| 迭代优化 | 第一次不满意就调 | 三轮出精品 |

记住这 8 个技巧，你的 Prompt 水平就能从"凑合能用"提升到"效果拉满"。
