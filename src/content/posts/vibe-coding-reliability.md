## 第一次听说这个词

上个月刷 X 的时候，看到 Andrej Karpathy 发了一条帖子。

Karpathy 是谁？前 Tesla AI 总监、OpenAI 创始成员、那个让全世界都知道了 transformer 的人。他发了这么一段话：

> "There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."

翻译过来就是：有一种新的编程方式，我叫它"氛围编程"。你完全沉浸在感觉里，接受所有生成的结果，甚至忘掉代码的存在。

他还说了一句话更狠的：

> "I just see things, say things, run things, and copy-paste things, and it mostly works."

我看到东西，说出来，跑一下，复制粘贴，大部分时候它能跑。

说实话，第一次看到这段话的时候，我心里的反应是：这哥们在开玩笑吧。

---

## 这不就是瞎搞吗

一个写了几十年代码的人，跟你说"忘掉代码的存在"？

编程的核心不就是理解逻辑、控制质量吗？你连代码都不看了，怎么知道 AI 写的东西是对的？怎么排查 bug？出了安全事故谁负责？

我当时的判断很明确：这是 Karpathy 在玩票，不是正经建议。普通人别学。

然后第二天，我就用 Vibe Coding 的方式干了一个活。

---

## 那天到底发生了什么

事情是这样的。我有个朋友让我帮他搞个简单的工具——把一批 CSV 文件里的数据清洗一下，去掉重复行、统一日期格式、合并到一个文件里。

以前这种活我会怎么干？打开编辑器，写个 Python 脚本，处理文件读写、数据清洗、异常处理，可能还要处理编码问题。半小时到一小时。

那天我刚好忙，就打开了 Claude Code，跟它说：

> "帮我写个脚本，把 data 文件夹里的所有 CSV 文件合并成一个，去掉重复行，日期格式统一成 YYYY-MM-DD。"

它给了我一个脚本。我看了一眼大概逻辑，嗯，pandas 读文件、去重、格式化日期、输出，没什么问题。

然后我说："加上进度条，文件多的时候不知道跑到哪了。"

它就加了个 tqdm 进度条。

我又说："有些文件可能是 GBK 编码的，处理一下。"

它又改了。

整个过程大概五分钟。我没仔细审查每一行代码，看了看大方向没问题就跑了。结果呢？跑通了，输出的文件也对。

---

## 这算 Vibe Coding 吗

按照 Karpathy 的定义，严格来说不算。我还是看了一眼代码，还是做了判断。

但那种感觉确实不一样。以前我写代码是"我知道每一行在干什么"，这次是"我大概知道它在干什么，细节我不太关心"。

这个"不太关心"就是 Vibe Coding 的核心。

后来我又试了几次。用 Cursor 生成一个 React 组件的样式，没细看 CSS 就用了；让 AI 帮我改一个配置文件，改完直接复制过去。

每次我都会问自己一个问题：如果这段代码出了问题，我能查出来吗？

答案是：大部分时候能，但不保证。

---

## 靠谱的部分

试下来，有些场景 Vibe Coding 确实好使。

像那个 CSV 处理脚本，用完就扔的东西，代码质量差点无所谓，能跑就行。想快速验证一个想法的时候也是，比如我想试试某个 UI 效果，让 AI 先生成个粗糙版本，能看个大概就够了。格式化数据、生成模板、批量改名这种机械活，AI 比我快，出错概率也不比我高。还有你本身就熟悉的领域——AI 给的代码你扫一眼就知道对不对，"不审查"其实是"不需要审查"。

---

## 不靠谱的部分

但另一些场景，Vibe Coding 就是在给自己挖坑。

核心业务逻辑不能含糊。我之前那篇《你有多久没手写过代码了》里写过，AI 改了一段代码，看着没问题，但它根本没理解业务逻辑。这种错误你看代码都看不出来，因为它"语法正确、逻辑自洽"，但就是不对。

需要长期维护的项目也一样。Vibe Coding 生成的代码，你当时不看，三个月后回头看——这代码谁写的？哦，是我让 AI 写的。那它为什么要这样写？不知道。怎么改？不知道。

涉及用户数据、支付、权限的东西，你敢不审查就上线？

还有学习阶段。如果你是个正在学编程的新手，Vibe Coding 就是毒药。跳过了所有基础训练，直接让 AI 帮你干活，那你永远学不会。

---

## 光谱，不是二选一

所以 Vibe Coding 不是一个"靠不靠谱"的二元问题，它是一个光谱。

光谱的一端是 Karpathy 说的那种极致状态：完全不看代码，全凭感觉。另一端是传统的手写代码：每一行都是你亲手写的，你完全理解。

大多数人在中间的某个位置。问题是，你得知道自己站在光谱的哪个位置，以及什么时候该往哪头移。

我现在的习惯是这样的：

- 琐碎的、一次性的、格式性的工作 → 往 Vibe 那头移，让 AI 干
- 核心的、长期的、有风险的工作 → 往手写那头移，自己掌控

这个边界不是固定的，随着你对 AI 能力的理解加深，你会越来越清楚什么时候可以"放松"，什么时候必须"收紧"。

---

## 最让我在意的一件事

试了这么多次 Vibe Coding，最让我在意的不是代码质量，而是我的能力变化。

有几次我发现自己在偷懒。不是那种效率高所以少干了活的偷懒，是我其实应该想清楚再让 AI 写，但没想清楚就让它写了。

区别在哪？你知道怎么做、让 AI 帮你干，那是利用工具。你不知道怎么做、让 AI 帮你干、祈祷结果是对的，那是依赖工具。Vibe Coding 很容易从前面滑到后面。滑过去的时候你根本感觉不到，因为代码还是"能跑"。直到有一天跑不通了，你才发现自己已经不会从头写一个了。

---

## 所以靠不靠谱

回到标题的问题：Vibe Coding 到底靠不靠谱？

我的答案是看你怎么用。当成效率工具，在合适的场景下用，它很靠谱。当成替代能力的捷径，它很不靠谱。

Karpathy 说"忘掉代码的存在"，但他是 Karpathy。他忘掉代码是因为他已经写了三十年代码，代码已经长在他脑子里了。你忘掉代码，是因为你从来没写过。

这两者的区别，就是 Vibe Coding 靠不靠谱的分界线。

有一件事是确定的：代码还在那里。你可以不看它，但它不会因为你不看就不存在。出问题的时候，你还是得自己面对它。

所以我的建议是：放心去 Vibe，但偶尔低头看看脚下。
